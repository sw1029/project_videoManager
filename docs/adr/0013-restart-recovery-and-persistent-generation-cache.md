# ADR-0013 재시작 복구와 생성 결과 캐시 영속화 (외부 작업 원장)

- 상태: 채택 (2026-11-12)
- 관련 이슈: #2 [운영] 재시작 복구, #7 [운영] 생성 결과 캐시 영속화와 기본 활성화

## 맥락
- inline·thread 디스패처는 작업을 프로세스 메모리에만 둔다 (ADR-0005). 2026-11-11 실제 실행 검증에서 생성 중에 서버를
  다시 시작하면 버전이 PROCESSING 으로 영구히 남았고, 다시 접수하면 409(`VERSION_NOT_GENERATABLE`)였다.
  OpenRouter 작업은 계속 돌아 과금되지만 결과를 회수하지 못했다. 접수만 된 QUEUED, 구조화 중인 STRUCTURING 도 같은 이유로 남는다.
- `CachingVideoGenerator` 는 프로세스 메모리 dict 였고 기본으로 꺼져 있었다. 같은 프로세스에서는 같은 조건 장면을 다시 제출하지
  않았지만(0회), 재시작 뒤에는 3장면을 모두 다시 제출했다 (장면당 약 $0.21 재과금).
- `SceneGenerationRequest.fingerprint` 는 IR 조건(장면·객체·참조 이미지 URI·seed)만 담는다. 그대로 캐시 키로 쓰면
  모델·해상도를 바꿔도 이전 결과가 나온다.

## 결정

### 1. 생성 결과 캐시 (#7)
- **키** = `generation_key(fingerprint, profile)` (정규화 JSON 해시). 프로필은 `VideoGenerator.profile()` 이다.
  기본값은 클래스 이름이고, OpenRouter 는 주소·모델·해상도·화면비·fps 를 낸다. 주소를 넣어 가짜 서버(로컬 시험)에서 만든 클립이
  실제 서버 요청에 쓰이지 않게 한다. 키에는 비밀(API 키)을 넣지 않는다.
- 컨테이너는 **데코레이터로 감싸기 전 생성기**의 프로필로 캐시를 만든다. 데코레이터가 `profile()` 을 넘기지 않더라도 키가 틀리지 않는다.
  (`RetryingVideoGenerator`·`CachingVideoGenerator` 는 감싼 생성기의 값을 돌려준다.)
- **저장 위치**: ArtifactStore 의 `cache/clips/<키>.json` (스키마 1: `key`, `profile`, `version_id`, `saved_at`,
  `clip{scene_key, uri, duration_ms, fingerprint, metadata}`). DB 테이블 대신 산출물 저장소를 고른 이유
  - 항목이 가리키는 클립과 수명이 같다. 산출물 폴더를 지우면 캐시도 사라지고, 메모리 저장소면 둘 다 프로세스와 함께 사라진다.
  - 생성기 어댑터가 DB(UnitOfWork)를 알 필요가 없고, 스키마 이전이 없다.
- 키로 바로 읽으려면 URI 를 계산해야 하므로 `ArtifactStore.uri_for(key)` 를 추가했다 (메모리·로컬 파일 구현). 계산할 수 없는 저장소는
  `None` 을 돌려주고, 그때는 프로세스 메모리 캐시로 대신한다.
- **적중 조건**: 항목을 읽을 수 있고 클립 산출물이 저장소에 실제로 남아 있을 때만. 깨진 항목·사라진 클립은 미적중이며, 다시 생성한 클립으로 항목을 덮어쓴다.
- **적중 표시**: `GeneratedClip` 은 불변이라 복사본의 metadata 에 `cache_hit: true`, `cache_key`, `cached_from_version_id` 를 더하고 INFO 로그를 남긴다.
  원래 metadata(비용 등)는 처음 생성할 때의 값이므로 비용을 합산할 때는 `cache_hit` 인 클립을 빼야 한다.
- 같은 키의 동시 요청은 하나만 생성한다 (키별 잠금). 생성 실패는 캐시하지 않는다. 캐시 기록이 실패해도 경고만 하고 생성한 클립을 돌려준다.
- `FRAME_GENERATOR_CACHE` 기본값을 **true** 로 바꾼다. 항목에는 기한이 없다 (클립이 남아 있는 동안 유효).

### 2. 외부 작업 원장 (#2, OpenRouter)
- 접수(202) 직후, **폴링 전에** `ledger/openrouter/<키>.json` 에 작업을 남긴다. 키는 캐시와 같은 `generation_key`.
  내용: `job_id`, `status`(submitted · completed · failed), `submitted_at`(벽시계), `version_id`, `scene_key`, `profile`,
  `details`(과금 초·seed·참조 이미지 수·프롬프트·예상 비용·generation_id), `clip_uri`, `clip_metadata`, `error`. 키·서명 URL 은 넣지 않는다.
- 같은 키의 요청은 원장을 먼저 본다.

  | 원장 | 동작 | `metadata.ledger` |
  |---|---|---|
  | submitted, 또는 completed 인데 클립이 사라짐 | 새로 제출하지 않고 **바로** 상태를 조회해 이어서 폴링·다운로드·정규화 | `resumed` |
  | completed 이고 클립이 남아 있음 | 제출·조회·다운로드 없이 그 클립 (캐시를 꺼도 재과금을 막는다) | `reused` |
  | 없음 · failed · 만료 · 읽을 수 없음 | 새로 제출 | `new` |

- **failed 로 바꾸는 경우**: 제공자 쪽 `failed`·`cancelled`·`expired`, 작업·결과 없음(404·410), 영상이 아닌 결과. 이번 요청은 `retryable=False` 로
  끝내고(자동 재제출 없음, ADR-0011 원칙 유지) 다음 요청이 새로 제출한다.
- **이어 받을 수 있게 남기는 경우**: 시간 초과, 인증 오류, 다운로드 일시 실패, 정규화 실패. 시간 초과로 FAILED 된 장면도 같은 조건으로 다시 생성하면 같은 작업을 이어 받는다.
- **만료 규칙**: 제출 뒤 24시간(`ledger_ttl_seconds`)이 지난 항목은 이어 받지 않는다 (경고 로그와 함께 새로 제출).
  OpenRouter 결과 보관 기간을 문서로 확인하지 못해 보수적으로 잡았다. 클립까지 저장한 결과는 생성 캐시가 기한 없이 재사용을 맡는다.
  - 보완 (2026-11-14, 감사 A-32): 기한은 **제공자에게 다시 물어야 하는 항목**에만 적용한다 — 결과를 아직 못 받았거나(`submitted`),
    받았지만 클립이 저장소에 없는 항목. 클립이 남아 있는 완료 항목은 기한 없이 그 클립을 돌려준다.
    ADR-0016·0021 뒤로는 생성 캐시에 없고 원장에만 있는 완료 결과(임시 결과, 편집이 거절된 뒤 조건 키로 남긴 사본)가 생겨,
    "클립까지 저장한 결과는 캐시가 맡는다" 는 전제가 더는 맞지 않았다. 그런 결과가 24시간 뒤 다시 제출(과금)되던 것을 막는다.
- 같은 장면의 동시 요청은 하나만 제출한다. 원장 읽기·쓰기 실패는 생성을 막지 않는다 (쓰기 실패는 ERROR 로그: 재시작하면 이어 받지 못한다).
- **남은 위험**: 제출 요청을 보내고 응답을 받기 전(약 1초)에 프로세스가 죽으면 작업 id 를 모른다. 이때 다시 요청하면 새로 제출된다 (이전과 같음).

### 3. 버전 실행 기록 (#2, ERD 확장)
- `video_versions` 에 `queued_at`(마지막으로 QUEUED 가 된 시각), `started_at`(마지막 실행 시작 시각), `attempt`(실행 시도 횟수, 기본 0)를 더한다.
  도메인 `VideoVersion` 에서는 `state` 바로 뒤의 키워드 전용 필드라 위치 인자 순서는 그대로다.
- 생성 접수(DRAFT→QUEUED) 때 `queued_at`, 실행 시작(QUEUED→PROCESSING) 때 `started_at` 과 `attempt+1` 을 **단계 실행 전에 커밋**한다.
  생성 도중 프로세스가 죽어도 '언제 몇 번째로 시작했는지' 가 남는다.
- SQLite·MySQL 의 DATETIME 은 시간대를 버리므로 UTC 로 되붙여 돌려준다 (늘 UTC 로 쓴다). `create_schema` 는 예전 개발 DB 에 없는 열을
  `ADD COLUMN` 으로 더한다 (지우거나 바꾸지 않음. 운영 MySQL 은 마이그레이션으로).
- 상태 전이 **PROCESSING → QUEUED** 를 더한다. 워커 유실 뒤 재시도에만 쓰며 API 로는 일어나지 않는다.

### 4. 복구 유스케이스와 기동 시점 (#2)
- `RecoverPendingVersions.execute(startup=...)`

  | 상태 | 기동 (`startup=True`) | 주기 검사 |
  |---|---|---|
  | QUEUED | `run_generation_pipeline` 다시 디스패치 | 건드리지 않음 (대기열에서 차례를 기다리는 중일 수 있다) |
  | STRUCTURING | `structure_requirements` 다시 디스패치 (구조화는 멱등) | 건드리지 않음 |
  | PROCESSING | 모두 워커 유실 | `started_at` 이 `FRAME_WORKER_LEASE_S` 를 넘기면 워커 유실 (시작 시각이 없는 예전 행도 유실) |

- **기동 때 PROCESSING 을 모두 회수하는 근거**: in-process 디스패처는 작업을 프로세스와 함께 잃고, 서버 프로세스 하나를 전제로 한다
  (Dockerfile 도 uvicorn 프로세스 하나). 리스만 쓰면 재시작 직후 최대 리스 시간만큼 PROCESSING 으로 남는다.
  외부 큐(Celery 등)를 붙이면 `reclaim_processing_on_startup=False` 로 두고 리스만 쓴다.
- **워커 유실**: `attempt < FRAME_WORKER_MAX_ATTEMPTS` 면 QUEUED(`queued_at`=지금)로 되돌려 다시 디스패치한다. 다시 실행해도 과금된 장면은
  생성 캐시·작업 원장으로 이어 받는다. 상한이면 `FAILED(WORKER_LOST)` 로 끝내고 메시지에 "시도 n/m" 을 남긴다.
- 상태 변경은 조건부 갱신(`try_transition`)이라 그 사이 워커가 끝낸 버전은 건드리지 않는다. 디스패치는 커밋 뒤에 한다.
  한 버전의 오류나 디스패치 실패가 다른 버전의 복구를 막지 않는다. 기동 복구와 주기 검사는 잠금으로 겹치지 않는다.
- **기동 시점**: FastAPI lifespan 의 시작 단계, 즉 **요청을 받기 전**에 기동 복구를 끝낸다. 그래서 새로 접수된 버전을 '사라진 작업' 으로 오인하는
  경쟁이 없다. 그 뒤 `FRAME_RECOVERY_INTERVAL_S` 마다 주기 검사 스레드(데몬)를 돌리고, 종료 때 멈춘다. 복구 실패는 로그만 남기고 기동을 막지 않는다.
  `FRAME_JOBS=inline` 이면 복구한 작업이 기동 중에 실행돼 기동이 늦어진다 (`thread` 권장).
- **설정**: `FRAME_WORKER_LEASE_S`=1800, `FRAME_WORKER_MAX_ATTEMPTS`=3, `FRAME_RECOVERY_INTERVAL_S`=60 (0 이면 기동 때만).
  리스는 버전 하나의 최대 처리 시간보다 길어야 한다. 실측(2026-11-11) 장면당 103~145초, 장면 시간 초과 600초이므로 3장면이면 최악 약 900초다.

## 결과
- 생성 중 재시작: 기동 복구가 PROCESSING 을 QUEUED 로 되돌려 다시 실행한다. 이미 제출한 장면은 원장으로 이어 받아 POST 0회,
  남은 장면만 제출해 COMPLETED 가 된다. 접수만 된 QUEUED 와 구조화 중이던 STRUCTURING 도 다시 실행된다.
- 같은 조건·같은 설정의 장면은 재시작 뒤에도 다시 생성하지 않는다. 모델·해상도·화면비·fps·주소를 바꾸면 다시 생성한다.
- 한계와 남은 일
  - 리스는 하트비트가 아니라 시작 시각 기준이다. 리스보다 오래 걸리는 정상 실행은 주기 검사가 회수해 두 번 실행될 수 있다.
    재과금은 캐시·원장이 막지만 낡은 실행이 결과를 덮어쓸 수 있으므로, 결과를 기록할 때 시작 때의 `attempt` 와 같은지 확인하는 것을 권한다.
  - 여러 서버 프로세스가 한 DB 를 쓰면 기동 복구가 다른 프로세스의 PROCESSING 을 회수한다 (in-process 디스패처는 원래 지원하지 않는 구성).
  - 캐시·원장 항목은 지우지 않는다 (작은 JSON). 정리는 산출물 폴더와 함께 한다.
  - SQL 저장소는 클립 metadata 를 저장하지 않으므로(ADR-0011 남은 일) 캐시 적중 기록은 로그와 캐시 항목에만 남는다.
  - API(`VersionOut`)에는 `queued_at`·`started_at`·`attempt` 를 아직 내보내지 않는다 (프론트 계약 변경은 따로).
  - LLM 응답 캐시(#7 의 선택 항목)는 하지 않았다.
  - 실호출 테스트(`tests/live/test_openrouter_live.py`)를 같은 조건으로 24시간 안에 다시 돌리면 원장이 이전 결과를 다시 쓰므로
    테스트가 실패하며 안내한다. 실제 호출을 다시 보려면 `<FRAME_ARTIFACT_DIR>/ledger/openrouter` 를 지운다.

## 대안
- 캐시·원장을 DB 테이블에: 메모리 DB + 로컬 산출물 조합에서 클립과 수명이 어긋나고, 생성기 어댑터가 UnitOfWork 를 알아야 하며 스키마 이전이 필요하다. 기각.
- 기동 때도 리스로만 PROCESSING 을 판단: 다중 프로세스에는 안전하지만 재시작 직후 최대 30분 동안 PROCESSING 으로 남는다.
  단일 프로세스 전제에서는 얻는 것이 없어 기각하고, 외부 큐용 스위치로 남긴다.
- 하트비트(실행 중 주기적으로 시각 갱신): 리스를 짧게 잡을 수 있지만 파이프라인 단계 안쪽(진행 기록, #3)을 건드린다. 후속으로 미룬다.
- 제출 전 '제출 중' 기록: 응답 전 종료를 알아챌 수는 있지만 자동으로 처리할 방법이 없다 (다시 제출하면 이중 과금 위험, 안 하면 장면이 막힘).

## 검증 (2026-11-12, 네트워크 없이)
- 테스트 455 통과 (`-m "not slow and not gpu"`), ruff check·format 통과. 실제 외부 API 호출과 서버를 띄운 e2e 는 하지 않았다.
- 캐시: 새 인스턴스·같은 산출물 폴더에서 같은 조건 0회 생성(계약 테스트), 컨테이너를 다시 조립해도 3장면 0회 생성,
  조건이 바뀐 장면만 생성, 프로필(모델·해상도·fps·주소) 변경 시 미적중, 클립 삭제·깨진 항목은 미적중, 동시 요청 1회 생성.
- 원장: 제출 뒤 프로세스 종료(BaseException) → 같은 산출물 폴더의 새 인스턴스가 이어 받음 → POST 정확히 1번. 완료 작업 재사용(요청 0회),
  클립 삭제 뒤 다시 받기(제출 없음), 시간 초과·인증 오류 뒤 이어 받기, 실패·404·만료·다른 설정은 새로 제출, 원장에 키·서명 URL 없음.
