# ADR-0016 수정 버전의 부모 클립 편집 포트와 실제 보존 검수기

- 상태: 채택 (2026-11-12)
- 관련: US-01 (AC-01), 성공 지표 1 "비대상 변경률 10% 이하", ADR-0003·0011·0013·0015
- 조사·실험 기록: [docs/research/character-consistency.md](../research/character-consistency.md)

## 맥락
- 수정 버전은 조건이 바뀐 장면만 다시 생성하고 나머지는 부모 클립을 재사용한다 (ADR-0003).
  재사용 장면은 바이트가 같지만, **다시 만든 장면 안**의 비대상 요소(구도·배경·인물)는 seed 가 같아도 바뀐다
  (2026-11-11 실호출, ADR-0011 "검증"). 컵 색만 바꿨는데 그 장면의 화면 전체가 새로 만들어진다.
- 픽셀 단위 편집은 이번 학기 Won't 지만, 장면 단위 안에서 "부모 클립을 입력으로 주고 바뀐 조건만 고치게" 하는 것은
  포트 하나로 붙일 수 있다. OpenRouter 에는 두 가지 길이 있다 (2026-11-12 공식 스키마·모델 페이지 32개 확인).
  - `previous_job_id`: "완료된 작업을 편집·연장. 같은 모델·엔드포인트에서 실행. 연속을 지원하는 모델만 받는다."
    모델 페이지의 요청 필드에 이 값을 적은 모델은 **없다** ("목록에 없는 값은 거부").
  - `input_references` 의 `video_url`: 영상 참조. 예시가 있는 모델은 FLUX Video Edit(편집 전용, $0.03/초),
    Runway Aleph 2.0($0.28/초), Seedance 2.0·2.0 Fast·2.0 Mini, Hailuo 3, HeyGen Video 1 이다.
- SQL 저장소는 클립 메타데이터(모델·작업 id)를 저장하지 않아(ADR-0011 남은 일), DB 를 거치면 부모 클립이 어떤 작업으로
  만들어졌는지 알 수 없었다.
- Fake 보존 검수기는 다시 만든 장면에 고정값(0.95)을 준다. 실제로 얼마나 달라졌는지 재는 수단이 없었다.

## 결정

### 1. 포트 확장
- `SceneGenerationRequest.parent: ParentClip | None`. `ParentClip` = 부모 버전 id · 부모 클립(생성 기록 포함) ·
  부모 쪽 장면 조건과 객체 정의. 생성 단계는 **조건이 바뀌어 다시 만드는 장면**에, 부모에 그 장면 클립이 있을 때 넘긴다.
- 부모 클립은 조건 fingerprint 에 들어가지 않는다 (재사용 판단은 그대로).
- 생성기는 둘 중 하나를 한다.
  - 편집하지 않는 생성기: 부모 클립을 무시하고 새로 만든다. `result_key` 가 부모와 무관하다 (Fake 는 기록만 한다).
  - 편집하는 생성기: 부모 클립을 고쳐서 만든다. 결과가 부모 클립에 달려 있으므로 `result_key` 에 부모를 넣는다.
- 어느 쪽이든 돌려주는 클립의 계약은 같다 (scene_key·길이·fingerprint). 계약 테스트로 고정했다.

### 2. 클립 메타데이터 저장
- SQL `scenes.clip_metadata_json` 에 클립 메타데이터를 저장한다 (예전 SQLite DB 에는 기동 때 열을 더한다).
  부모 클립의 모델·작업 id 가 DB 왕복 뒤에도 남는다.

### 3. OpenRouter 어댑터 (`FRAME_VIDEO_EDIT_MODE`, 기본 off)
- `previous_job`: 부모 클립의 생성 기록에 같은 모델의 작업 id(`gen-vid-<숫자>-<영숫자 20>`)가 있으면
  `previous_job_id` 로 이어서 편집한다.
- `video_reference`: 부모 클립을 `input_references` 의 `video_url` 로 편집 모델(`FRAME_VIDEO_EDIT_MODEL`,
  비우면 생성 모델)에 보낸다. 모델 메타데이터에 없는 선택 값(길이·해상도·화면비·seed·오디오)은 보내지 않는다.
  - 영상 참조는 **HTTPS 주소만** 받는다 (data URI 는 접수 전 400 `Only HTTPS URLs are allowed`, 실호출로 확인).
    그래서 부모 클립을 만든 OpenRouter 작업의 상태를 조회해 저장본의 서명 URL(`urls[0]`)을 그 자리에서 받아 넘긴다.
    부모 클립이 이미 HTTPS 주소에 있으면(원격 저장소) 그 주소를 그대로 쓴다.
  - 서명 URL 은 요청 본문에만 쓴다. 클립 메타데이터·원장·로그·오류 메시지에 남기지 않는다 (오류 메시지의 URL 은 호스트까지만 남긴다).
  - 저장본이 없거나 만료됐으면(작업 생성 약 24시간 뒤) 제출하지 않고 새로 생성한다.
  - **끝난 작업의 상태 응답에 저장본 주소가 빠져 올 때가 있다** (2026-11-12 2차 실호출). 같은 작업을 10번 물으면
    2~3번은 `urls` 없이 왔고, 끝난 지 6분 된 작업 둘은 한 번 물었을 때 주소가 없어 편집 대신 새로 생성됐다.
    그래서 '끝났는데 주소가 없는' 응답과 일시적인 조회 실패(연결 오류·429·5xx)는
    `FRAME_VIDEO_EDIT_PARENT_WAIT_S`(기본 10초) 동안 다시 묻는다: 처음 여섯 번은 2초 간격, 그 뒤로는 폴링 간격.
    없어진 작업(404·만료)은 다시 묻지 않는다. 조회 횟수는 `edit.parent_url_lookups` 에 남긴다.
- 편집 지시문은 부모 쪽 조건과 지금 조건의 **차이만** 적는다 (바뀐·더해진·빠진 조건, 관계 상대, 설명 변경) +
  "나머지는 입력 영상 그대로". 차이가 없으면 편집하지 않는다.
- 편집하지 않는 경우: 장면 길이나 등장 객체가 달라짐, 부모 클립이 없거나 영상이 아님, (`previous_job`) 작업 id 가 없거나 모델이 다름,
  (`video_reference`) 부모 클립에 OpenRouter 작업 id 도 HTTPS 주소도 없음.
- **접수 전에 거절되면(400·404·413·415·422) 새로 생성한다.** 과금되지 않은 거절이므로 ADR-0011 의 재과금 방지 원칙과 어긋나지 않는다.
  인증·크레딧·서버 오류와 접수 뒤 실패는 그대로 실패한다 (자동으로 다시 보내지 않는다).
- 거절 뒤에 같은 장면을 두 번 생성하지 않는다. 편집할 요청의 키에는 편집 방식·모델·부모 작업이 들어가 새로 생성할 때의 키
  (조건 + 정체성 기준)와 다르므로, 원장을 두 키로 본다.
  - 거절되면 조건 키로 이미 끝난 결과가 있는지 먼저 찾아, 있으면 제출하지 않고 그것을 쓴다.
  - 거절 뒤 새로 생성한 결과는 조건 키로도 남긴다. 편집 모드·편집 모델을 바꾸거나 편집을 꺼도 그 결과를 다시 쓴다.
    (편집 설정의 키로만 남겼을 때 실호출에서 같은 장면을 한 번 더 생성했다.)
- 클립 메타데이터의 `edit` 에 방식·모델·부모 클립·적용 여부(`applied`)·대체 사유를 남긴다.
- 편집으로 만든 클립도 지금까지와 같이 ffmpeg 로 장면 길이·해상도·fps 에 맞춘다.

### 4. 실제 보존 검수기 `ssim_preservation`
- 재사용 장면은 1.0. 다시 만든(또는 편집한) 장면은 부모 클립과 자식 클립의 프레임별 SSIM 평균 (ffmpeg `ssim`).
  임계값(`FRAME_PRESERVATION_THRESHOLD`, 0.9) 이상이면 PASS, 아니면 FAIL + 그 장면 구간 경고.
- `change_rate = 1 − SSIM` 은 비대상 변경률의 **상한**이다. 화면 전체를 비교하므로 일부러 바꾼 대상의 변화도 들어 있다.
  대상 영역을 빼려면 추적 박스·마스크가 필요하다 (AC-34, 실제 추적기 뒤).

## 결과
- 편집 모드를 켜면 수정 버전에서 바뀐 장면이 부모 클립을 입력으로 받아 만들어진다. 끄면 예전과 같다.
- 편집 모델이 요청을 받지 않아도 수정은 실패하지 않는다 (새로 생성).
- 한계
  - `previous_job_id` 는 스키마에는 있지만 받는 모델을 찾지 못했다 (모델 페이지 32개, Wan 3.0 은 실호출에서 거절).
    받는 모델이 생기면 설정만 바꾸면 된다.
  - `video_reference` 는 부모 작업의 저장본이 살아 있는 동안(약 24시간)만 된다. 그 뒤의 수정은 새로 생성한다.
    더 오래 쓰려면 클립을 HTTPS 로 내줄 저장소가 필요하다.
  - 방금 만든 클립은 저장본 주소가 늦게 나온다 (2차 실호출: 끝난 뒤 6분에는 없었고, 9~18분 사이에 나오기 시작했다).
    기본 설정(10초)으로는 생성 직후의 수정이 새로 생성으로 처리될 수 있다. `FRAME_VIDEO_EDIT_PARENT_WAIT_S` 를
    늘리면 주소가 나올 때까지 기다렸다가 편집한다 (기다리는 동안 그 장면의 생성 단계가 멈춰 있다).
    변경 계획을 먼저 보면 그때 받은 주소를 메모리에 들고 있다가 쓰고, 편집하지 못하면 미리 알려 준다
    ([ADR-0020](0020-production-preview-and-held-parent-url.md)).
    주소를 못 받아 새로 생성한 결과는 그 편집 요청의 키에도 남으므로, 같은 부모에서 같은 수정을 다시 요청하면
    그 결과를 다시 쓴다 (편집으로 다시 만들려면 새 수정 버전에서 고치거나 유지할 요소를 바꾼다).
  - 편집 모델은 생성 모델과 다른 모델이라 화질·색감이 달라질 수 있고, 편집 결과의 정체성 일관성은 따로 검수해야 한다.
    편집한 클립을 부모로 다시 편집할 때의 화질 저하는 확인하지 못했다.
  - SSIM 은 구조 유사도다. 색만 바뀐 큰 영역은 덜 깎이고, 작은 위치 이동에는 크게 깎인다. 편집 모델은 프레임 전체를 다시 만들어 내므로
    바뀌지 않은 영역도 픽셀 단위로는 달라져, 눈으로는 같은 화면이어도 임계 0.9 에 못 미칠 수 있다 ("검증").

## 대안
- 편집 모델을 별도 포트(`VideoEditor`)로: 파이프라인이 "편집할지 새로 만들지" 를 알아야 하고 캐시·원장·시간 제한 데코레이터를
  한 번 더 엮어야 한다. 요청에 부모 클립을 싣는 편이 변경이 작다.
- 접수 뒤 실패한 편집 작업도 자동으로 새로 생성: 과금 여부를 알 수 없어 기각 (ADR-0011).
- 부모 클립을 data URI 로 보내기: 처음 구현한 방식. 영상 참조는 HTTPS 주소만 받아 실호출에서 거절됐다. 기각.
- 클립을 공개 저장소에 올리고 그 주소를 넘기기: 보관 기한에 묶이지 않지만 저장소와 서명 URL 발급이 필요하다. 후속.

- 단위·계약 테스트 (네트워크 없이): `tests/unit/generator/test_openrouter_edit.py`(편집 지시문, 두 모드의 요청 본문, 서명 URL 을 남기지 않음,
  거절 뒤 새로 생성과 원장 재사용, 결과 키), `tests/contract/test_generator_contract.py`(부모 클립을 받아도 계약이 같음),
  `tests/contract/test_checker_contract.py`·`tests/integration/test_real_checkers_pipeline.py`(SSIM 보존 검수),
  `tests/integration/test_consistency_api_flow.py`(루프백 가짜 OpenRouter 로 API 전체 흐름).
- 실호출 (2026-11-12, 컵 색 red → teal, 장면 2개 편집. 자세한 표와 그림은 연구 문서 §6.4)

  | 방식 | 결과 | SSIM `show_cup` | SSIM `cup_closeup` | 건당 시간·비용 |
  |---|---|---|---|---|
  | 새로 생성 (Wan 3.0, 정체성 기준 포함) | 인물은 같지만 자세·배경·구도가 바뀜. 한 번은 컵 색이 바뀌지 않음 | 0.541 · 0.556 | 0.780 · 0.757 | 100~145초, $0.2125 |
  | `video_reference` + FLUX Video Edit, data URI | 접수 전 400 (HTTPS 만) → 새로 생성 | — | — | 과금 없음 |
  | `video_reference` + FLUX Video Edit, 서명 URL | **편집 적용.** 같은 인물·자세·배경·구도에서 컵 색만 바뀜 | **0.745** | **0.900** | 41~50초, $0.12 |
  | `previous_job` (Wan 3.0) | 접수 전 400 `does not support previous_job_id` → 새로 생성 | — | — | 과금 없음 |

  - 서로 다른 두 장면끼리의 SSIM 이 0.50~0.60 이다. 새로 생성한 장면은 그 수준이고, 편집한 장면은 뚜렷이 높다.
- 2차 실호출 (2026-11-12, [concept-ux-review.md](../research/concept-ux-review.md) §5·§6.3)
  - 방금 만든 4장면 영상을 바로 수정했더니(끝난 지 6분 된 작업 둘) 상태 응답에 저장본 주소가 없어 두 장면 모두 새로 생성됐다.
    과금 없는 상태 조회로 재 보니 Wan 3.0 작업 6건의 주소는 끝난 뒤 2분 안(1건)·5~11분(3건)·14~18분(2건)에 처음 보였고,
    FLUX 편집 작업 2건은 1분 안팎이었다. 주소가 보인 뒤에도 응답에서 빠진다: 1.5초 간격으로 10번 물으면 2~3번,
    30초 간격으로 20분쯤 물으면 40번 가운데 12~13번이었고 길게는 7번 연속(약 3.5분)으로 빠졌다.
    기본 10초의 재조회는 응답 한두 번에서 빠지는 경우만 넘긴다.
  - 다시 묻게 고친 뒤 같은 원본을 수정: 한 장면은 두 번째 조회에서 주소를 받아 편집됐다 (`parent_url_lookups=2`).
    같은 원본에서 새로 생성 대 편집은 생성 단계 318초 대 99초, $0.425 대 $0.24, SSIM 0.490·0.680 대 0.664·0.828 이었다.
  - 주소를 주지 않는 시험 서버로는 여섯 번(10초) 묻고 새로 생성으로 넘어갔고, 사유가 `edit.fallback_reason` 에 남았다.
  - 편집한 `show_cup` 은 0.745 로 임계 0.9 에 못 미쳐 보존 검수는 FAIL 이다. 눈으로는 컵 색만 바뀌었다.
    변경 영역을 빼고 재는 지표(추적 박스·마스크)가 있어야 AC-01 을 공정하게 판정할 수 있다.
  - 거절 뒤 새로 생성한 결과를 조건 키로도 남기는 수정(§3)은 실호출 한도를 다 쓴 뒤라 단위 테스트로만 확인했다.
