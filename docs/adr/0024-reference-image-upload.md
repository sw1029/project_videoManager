# ADR-0024 참조 이미지 업로드

- 상태: 채택 (2026-11-14)
- 관련: 이슈 #12, 시스템 구조 설계 §3.2 Endpoint Catalog (`POST /api/projects` 는 "요구사항·참조 이미지를 접수"),
  ADR-0009 (프론트 연동 계약) · 0015 (정체성 기준 이미지) · 0019 (참조 이미지 HTTP 경로) · 0023 (IR 직접 입력)

## 맥락
- `POST /api/projects` 는 참조 이미지를 URI 문자열(`reference_images[].image_uri`)로만 받았다. 화면에서 파일을 올릴 방법이 없었다.
- 이미 있는 것: 버전의 참조 이미지를 내려받는 경로(`GET /versions/{id}/reference-images/{rid}`, 저장소에 있는 URI 만, 저장 루트 밖·
  외부 주소는 404), 수정 버전이 참조 이미지를 물려받는 것, 생성 요청에 사용자 참조를 싣는 것(OpenRouter 는 저장소의 이미지를 data URI 로).
- 저장 키는 `refs/{project_id}/...` 로 두기로 했지만, 화면은 보통 이미지를 먼저 올리고(미리보기) 프로젝트를 나중에 만든다.
  올릴 때는 프로젝트 id 가 없다.

## 결정

### 1. 업로드 경로 `POST /api/reference-images` (multipart/form-data, `file` 필드)
- 응답은 201 `{image_uri, media_type, size_bytes}`. 화면은 `image_uri` 를 `POST /api/projects` 의 `reference_images[].image_uri` 에 쓴다.
- 형식은 **파일 내용의 첫 바이트로** 판별한다: PNG·JPEG·WebP 만 받고 그 밖은 415 `UNSUPPORTED_MEDIA_TYPE`.
  올린 쪽의 파일 이름과 형식 표기(Content-Type)는 쓰지 않는다.
- 크기 상한은 `FRAME_REFERENCE_IMAGE_MAX_BYTES` (기본 10 MiB). 넘으면 413 `PAYLOAD_TOO_LARGE`.
  본문을 받기 전에 선언된 크기를 본다: `Content-Length` 가 없으면(chunked) 411 `LENGTH_REQUIRED`, 상한(+ multipart 머리글
  여유 64 KiB)을 분명히 넘으면 413. FastAPI 는 의존성보다 먼저 본문을 다 받아 임시 파일에 쓰므로, 크기를 밝히지 않은 요청을
  받아 주면 요청 하나가 임시 디스크를 얼마든지 채울 수 있다 (감사 4). 브라우저의 `FormData` 업로드는 늘 크기를 밝힌다.
  그다음 파일을 상한 + 1 바이트까지만 읽어 판단한다. `file` 이 없거나 빈 파일이면 422.
- 요청 제한(`FRAME_RATE_LIMIT_PER_MINUTE`)을 다른 변경 요청처럼 받는다.
- 의존성: FastAPI 의 파일 업로드가 쓰는 `python-multipart` 를 더한다 (사용자 승인). 0.0.18 미만은 잘못된 경계로 서비스를
  멈추게 하는 취약점이 있어 `>=0.0.18,<0.1` 로 둔다.

### 2. 임시 자리에 받고, 프로젝트를 만들 때 옮긴다
- 올린 이미지는 `refs/uploads/{upload_id}.{ext}` 에 둔다. 키는 서버가 만든 id 와 판별한 형식의 확장자로만 짓는다.
- `POST /api/projects` 가 그 URI 를 받으면 `refs/{project_id}/{reference_image_id}.{ext}` 로 복사하고, 버전의 참조 이미지에는
  옮긴 URI 를 남긴다. 그래서 버전에 남는 업로드 이미지는 모두 `refs/{project_id}/` 아래에 있다 (글·블록 IR 입력 모두).
- 업로드로 인정하는 URI 는 이 저장소의 임시 자리 URI 와 정확히 같은 것뿐이다 (이름은 서버가 짓는 모양, `uri_for` 로 다시 만든 값과 같음).
  그 밖의 URI(외부 주소, 직접 지정한 저장소 URI)는 지금처럼 그대로 남긴다. 업로드처럼 보여도 모양이 다르면 옮기지 않는다.
- 업로드 URI 인데 저장소에 없으면(지워졌거나 메모리 저장소가 다시 시작됨) 아무것도 저장하지 않고 422.
- 옮긴 뒤의 일은 그대로다: 내려받기 경로(`image_url`), 수정 버전으로 복제, 생성 요청의 사용자 참조.

### 3. 지키는 것
- 내려받기 경로의 검사(저장소에 있는 URI 만, 저장 루트 밖 경로·외부 주소는 404)는 바꾸지 않았다.
- 업로드 키에 사용자 입력이 들어가지 않으므로 업로드로 저장 루트 밖에 쓸 수 없다.
- 인증은 없다 (ADR-0009 의 남은 과제). 업로드 URI 를 아는 사람은 누구나 그 이미지를 자기 프로젝트에 쓸 수 있다.
  운영 설정의 업로드 id 는 UUID(`UuidIdGenerator`)라 추측하기 어렵다.

## 결과
- 화면에서 올린 이미지가 버전의 참조 이미지로 저장되고(`refs/{project_id}/`), 내려받을 수 있고, 생성에 쓰이고, 수정 버전에 복제된다.
- 한계
  - 임시 자리의 원본은 지우지 않는다 (저장소 포트에 삭제가 없다). 프로젝트에 쓰이지 않은 업로드도 남는다. 정리 작업이 따로 필요하다.
  - URI 를 미리 계산할 수 없는 저장소(`uri_for` 가 None 인 원격 저장소)에서는 옮기지 않고 임시 자리 URI 를 그대로 쓴다.
  - 같은 업로드를 여러 프로젝트에 쓰면 프로젝트마다 복사본이 생긴다.
  - 생성기는 참조 이미지를 data URI 로 보내므로 큰 이미지는 요청을 키운다. 상한을 더 줄일지는 실제 사용을 보고 정한다.
  - 버전을 만든 뒤에 참조 이미지를 더하는 경로는 없다 (수정 버전도 부모의 참조를 물려받을 뿐이다).

## 대안
- `POST /api/projects` 를 multipart 로 (요구사항 JSON + 파일): 프로젝트 id 를 먼저 만들 수 있지만 JSON 본문과 파일을 한 요청에 섞어
  스키마·검증·화면 코드가 복잡해지고, 미리보기용으로 먼저 올리는 흐름에 맞지 않는다.
- 이미지 바이트를 본문 그대로 받기 (`Content-Type: image/png`, 의존성 없음): 사용자가 multipart(이슈 문구 그대로)를 골랐다.
- 업로드를 `refs/uploads/` 에 그대로 두기: 키 규칙(`refs/{project_id}/`)을 지킬 수 없고 프로젝트별로 정리할 수 없다.
- 저장소 포트에 삭제·이동을 더하기: 옮긴 뒤 원본을 지울 수 있지만 포트와 모든 구현을 바꿔야 한다. 정리 작업과 함께 정한다.
