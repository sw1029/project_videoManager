# ADR-0023 IR 직접 입력·DRAFT IR 수정과 객체의 표시 이름

- 상태: 채택 (2026-11-14)
- 관련: US-06 (AC-13), 이슈 #10·#11, 문제정의서 리스크 2, 아이디어 3·페이퍼 프로토타입 ①(블록 입력, T4),
  ADR-0002 (모델 비의존 IR) · 0004 (IR 이중 저장) · 0007 (IR 규칙) · 0017 (수정 의도)
- 근거: [STRUCTURING_DESIGN.md](../STRUCTURING_DESIGN.md) §3·§7.2·§9, [concept-ux-review.md](../research/concept-ux-review.md) §3.1

## 맥락
- 화면 ①은 [인물]·[배경]·[소품]·[행동] 블록 입력이다. 화면이 블록을 IR 로 조립해도 받을 API 가 없었다
  (`POST /api/projects` 는 `prompt` 필수, 늘 비동기 구조화).
- 리스크 2 의 대응은 "구조화 결과의 사용자 확인·수정" 인데, DRAFT 의 IR 을 고치는 API 가 없었다.
  화면이 블록을 고쳐도 반영할 수 없었다.
- 객체의 키(`entity_key`)는 요구조건 키·추적 경로·DB id 에 쓰이는 영문 식별자다. 화면 라벨("컵 01", "바리스타")을 둘 자리가 없었다.
  설명(`description`)은 생성 지시문과 장면 조건(fingerprint)에 들어가므로, 라벨로 쓰면 이름만 바꿔도 장면이 다시 만들어진다.

## 결정

### 1. IR 문서 보정 포트 `IrDocumentStructurer` (구현 `PassthroughStructurer`)
- IR 문서(`IR.to_dict` 형식)를 결정적 보정(`light_repair`) → IR 변환 → `validate` 만 거쳐 IR 로 만든다.
  LLM 구조화와 같은 보정 규칙이므로 입력 방식이 달라도 같은 IR 규칙으로 모인다.
- 결과는 IR 과 보정 메모(`repair_notes`: 장면 구간 이동·객체 연결·종류 별칭 정리 등). 고칠 수 없는 문서는 `ValidationError`(422).
- 보정 규칙은 어댑터(`adapters/structurer/repair.py`)에 있으므로 애플리케이션은 포트로만 부른다.
  설정 키는 두지 않는다 (바꿔 끼울 구현이 없다. 전파 정책처럼 컨테이너 `overrides["ir_structurer"]` 로 바꾼다).
- 구조화 보고서(`StructuringReport`, #16)는 보류 그대로다. 보정 메모는 응답으로만 돌려주고 저장하지 않는다.

### 2. IR 직접 입력 — `POST /api/projects {ir}` (#10)
- `prompt` 와 `ir` 가운데 하나는 있어야 한다 (둘 다 없으면 422).
- `ir` 이 있으면 요청 안에서 보정·검증하고 바로 DRAFT 를 만든다. 구조화 작업을 넘기지 않으며 응답은 **201** + `state=DRAFT` + `repair_notes`.
  글만 있으면 지금처럼 202 + `STRUCTURING`.
- 둘 다 오면 `ir` 을 우선하고 글은 `source_prompt` 로만 남긴다 (기록·재현용, 구조화에 쓰지 않는다).
- 자연어 구조화와 같은 확인을 한다 (`application/structuring_rules.py`): 참조 이미지가 가리키는 객체가 IR 에 있어야 하고,
  목표 길이를 줬으면 장면 합계가 허용 오차 안이어야 한다. 하나라도 어긋나면 아무것도 저장하지 않는다 (422).
- 상태 기계에서 이 경로는 STRUCTURING 을 거치지 않고 DRAFT 로 태어난다 (수정 버전이 DRAFT 로 태어나는 것과 같다).
- 입력 상한 (공개 데모의 생성 비용 보호): 장면 60·객체 50·장면당 요구조건 50, 장면 길이 합계 5분.
  보정이 장면을 0.5초보다 짧게 두지 않으므로 합계도 그 값으로 센다.

### 3. DRAFT IR 수정 — `PUT /api/versions/{version_id}/ir` (#11)
- 본문은 IR 문서다. GET 의 `ir` 과 같은 모양이며 읽기 전용 필드(`entity_id`·`requirement_key`·`clip_url` 등)는 무시하므로,
  화면은 받은 `ir` 을 고쳐 그대로 보내면 된다.
- DRAFT 이고 조건이 고정되지 않은 버전만 고친다. 그 밖에는 409 `VERSION_NOT_EDITABLE` (고정된 뒤의 변경은 `POST /revisions`).
- 응답(`EditDraftIrOut`)은 고친 뒤의 버전(GET 과 같은 모양) + `repair_notes`.
- 저장은 조건부 갱신 `VersionRepository.replace_draft_ir` 이다:
  `UPDATE video_versions SET ir_json=? WHERE version_id=? AND state='DRAFT' AND frozen_fingerprint IS NULL` 로 행을 잡은 뒤
  정규화 행(장면·장면-객체·요구조건)을 다시 만든다. IR 외의 필드는 쓰지 않으므로, 읽은 뒤 생성이 접수됐으면 0 행으로 끝나 409 를 내고
  고정된 IR·상태를 되돌리지 않는다 (무결성 규칙 1). `save()` 는 버전 행 전체를 쓰므로 이 용도에 쓰지 않는다.
- 원문·seed·참조 이미지는 그대로다. 사용자가 올린 참조 이미지(USER)가 가리키는 객체를 IR 에서 지우면 422.
  정체성 기준 이미지(DERIVED)는 막지 않는다 (객체가 없어지면 쓰이지 않을 뿐이다).
- 목표 길이는 확인하지 않는다. 목표 길이는 자동 구조화에 주는 조건이고, 사람이 고친 길이가 곧 목표다.
- 수정 버전의 DRAFT 도 고칠 수 있다 (사용자 결정, 2026-11-14: 계속 허용). 이때 수정 의도(`intent`, ADR-0017)는 처음 값 그대로다.
  다시 만들 장면은 지금처럼 조건 비교(장면 fingerprint)로 정해지고, 생성 지시의 '꼭 지킬 값'은 지금 IR 에서 의도의 값과 같은
  요구조건만 싣는다 (PUT 으로 값을 바꾸면 빠진다). 그래서 의도와 실제 변경이 달라질 수 있다. 실제로 바뀐 장면은 전후 비교
  (`GET /comparison` 의 `conditions_changed`)가 알려 준다. 수정 의도대로 고치려면 계획·수정 API 를 쓴다.

### 4. 객체의 표시 이름 `EntitySpec.display_name` — 채택
- 화면에 보여 줄 이름이며 선택이다. 비어 있으면 화면이 종류와 순번으로 라벨을 만든다 (컨셉 화면의 "컵 01 · 인물 01 · 배경 01").
  블록 입력에서 사용자가 붙인 이름("바리스타")은 여기에 둔다. 키는 영문 snake_case 식별자로 남는다.
- **생성 조건이 아니다.** 장면 fingerprint·생성 fingerprint·정체성 외형 해시에 넣지 않고 생성 지시문에도 쓰지 않는다.
  그래서 이름만 바꾼 장면은 다시 만들지 않고 부모 클립을 쓴다.
- IR 문서에는 값이 있을 때만 들어간다. 그래서 표시 이름이 없던 문서와 그 IR fingerprint 는 그대로다.
  조건 고정 fingerprint 에는 들어간다 (고정 뒤에는 이름도 바뀌지 않는다).
- 저장: `entities.display_name` (NULL 허용, 예전 개발 DB 는 기동 때 열을 더한다). API: `EntityOut.display_name`(없으면 null),
  `IREntityIn.display_name`(64자).
- 바꾸는 방법: DRAFT 에서 `PUT /ir`. 고정된 버전의 이름은 바꿀 수 없다.
- 이번에 하지 않은 것: LLM 구조화가 표시 이름을 채우게 하는 것 (구조화 출력 스키마·프롬프트 버전이 바뀌므로 골드셋 평가 #17 뒤로),
  변경 요청 해석기가 표시 이름("컵 01 색 바꿔줘")을 읽게 하는 것, 규칙 기반 DSL 문법.

## 결과
- 화면이 자연어 없이 블록 IR 로 DRAFT 를 만들고(201), 구조화 결과를 고친 뒤(`PUT /ir`) 생성을 접수할 수 있다. 고정된 IR 은 바뀌지 않는다.
- 글·블록·DSL 세 입력이 같은 보정·검증을 거친다.
- 한계
  - 보정 메모는 저장되지 않는다 (보고서 #16 보류). 다시 보려면 같은 문서를 다시 보내야 한다.
  - `entities` 행은 프로젝트 범위라 표시 이름은 마지막으로 저장한 버전의 값이 남는다. 도메인 복원은 IR 문서에서 하므로 버전마다 정확하다.
  - 동시 접수 경쟁의 실제 다중 스레드·MySQL 검증은 #4 에 남는다 (메모리·SQLite 계약 테스트와 유스케이스의 경합 재현만 했다).

## 대안
- 표시 이름을 `description` 에 두기: 이름만 바꿔도 장면이 다시 만들어지고 생성 지시문이 바뀐다.
- 표시 이름 없이 화면이 늘 종류·순번으로 만들기: 블록 입력에서 사용자가 붙인 이름을 남길 곳이 없고, 이름을 남기려면 키를 한글로 쓰게 된다
  (요구조건 키·추적 경로·DB id 에 그대로 들어간다).
- IR 직접 입력도 202 + 비동기 작업으로: 보정·검증은 바로 끝나는 결정적 계산이라 작업을 거칠 까닭이 없고, 화면이 보정 결과를 바로 보여 줘야 한다.
- 수정 API 를 `save()` 로 저장: 읽은 뒤 생성이 접수되면 버전 행 전체를 써서 상태와 고정 fingerprint 를 되돌린다.
